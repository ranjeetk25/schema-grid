# 0.4.1: admissions integration fixes

Status: approved (2026-09-28). Patch release, all six packages, all changes additive. Source: reports from the admissions.space2 integration of 0.4.0.

## F1. Color store availability (server)

`createSqlViewDataSource` and `createDrizzleDataSource` never call `CellColorStore.available()`. With `colors` passed and the table missing, every `fetch` fails with `MISSING_TABLE`.

- Both sources check `colors.available()` once per data-source instance, lazily and cached, mirroring how the registry gates `SchemaStore.available()`. Unavailable means the source behaves exactly as if no store were passed:
  - no join/subquery and no `colors` on rows
  - `capabilities.cellColors = { read: false, write: false, filter: true }`
  - `setCellColors` absent, or answering like the no-store path
- Add `reset()` on the color store to drop the cached probe (the backlog asked for the same on the other stores; do it for the color store now).
- Tests: unit tests with a probe stub, plus MySQL integration with the table dropped (fetch succeeds, no colors, capabilities false).

## F2. Color rules that the server cannot evaluate (core, server, both UI kits)

A rule's `when` is validated as a normal filter. Columns the server can't filter on in SQL are:
- `filterable: false` columns
- SQL-view computed columns, which are forced to `filterable: false`
- `mapRows`-derived values that are NULL in SQL

Such rules (a) make any `colorIs` query fail with a misleading `Column "Verdict" cannot be filtered`, and (b) could never be SQL-filtered correctly anyway.

Contract:
- **Core `validateColorRules`** accepts `filterable: false` columns inside `when`. Rules render client-side from row values, so this is valid for rendering. Readability, operator/value checks and `colorInRule` stay.
- **Core helper (new):**
  `colorFilterBlockers(columnId: string, rules: readonly ColorRule[] | undefined, schema: GridSchema, isSqlFilterable: (columnId: string) => boolean): ColorRule[]`
  It returns the enabled rules that can affect `columnId`'s shown color (`cells` rules targeting it, and all `row` rules) whose `when` references a column for which `isSqlFilterable` is false. The default predicate is `column.filterable !== false`, and it must also respect the capabilities `filter` scope when one is given; expose a `(schema, capabilities?)` factory for the predicate.
- **Server:** when a query carries `colorIs`/`colorIsNone` on column `c` and `colorFilterBlockers(c, …)` (using the server's effective schema, where computed columns are unfilterable) is non-empty, answer 400 `FILTER_INVALID` with the message:
  `Can't filter "<label of c>" by color: a color rule on it uses "<label of first offending column>", which can't be filtered on the server`.
  Otherwise compile as today; rules that can't affect `c` are ignored.
- **ag-grid + both UI kits:** hide or disable "Color is…", the header "Filter by color" submenu and the filter-builder color operators for a column whose blockers are non-empty. Show the reason as a tooltip or hint where the kit has one. Keep this consistent with the capability gating that already exists. `columnOperatorsWithColors` gains an optional rules/schema input, additive, so it can drop color operators for blocked columns.
- **Rules dialog:** allow picking unfilterable columns in a rule's condition (the rule still renders). Show a subtle note on such a rule: "Can't be used to filter by color".
- **Reproduce first:** add a server test with a SQL-view computed column `verdict`, a `cells` rule targeting `verdict` whose `when` tests `verdict`, and `colorIs` on `verdict`. Today this fails with "cannot be filtered"; after the fix it gets the new, clear 400. Also test the passing case, where a rule on a filterable column is filtered correctly.

## F3. Per-person refusal message (server, core)

Whenever an edit is denied by `permissions.edit` (the user matches neither `roles` nor `users`) and the column is otherwise writable (not a formula, `settable !== false`), the refusal is `"Only specific people can edit this column"`. Never list ids or roles. Keep `"Column is read-only (formula)"` for formulas and `"Column is read-only"` for `settable: false`. This applies to all write paths: `plan-changes.ts`, `rows-crud.ts`, SQL-view update/create, `setCellColors` rejections, and the client-side `editController` pre-check (the same message there).

## F4. `defineGrid` user warning (server)

When `redactPermissionUsers` is on and the `user` resolver (explicit or the `ctx.user` default) yields no user, or a user without a `roles` array, log a one-time `console.warn` per grid id, only when `process.env.NODE_ENV !== "production"`. Say that per-person lists are being emptied, and how to pass `defineGrid({ user })`. Tests with a spy.

## F5. Capability-gated field types (core, server, both UI kits)

This is the "Capability-gated field types" item in `docs/TODO.md`:
- core `fieldTypeAvailability(typeId, capabilities)` returns `{ available, reason? }`: `link` needs `lookup`, `user` needs `options`, and custom types can declare requirements additively.
- The column builder takes `capabilities` (the workbench passes `effectiveCapabilities`) and hides unavailable types. An existing column keeps its type, shown with the reason.
- LinkPicker, UserPicker and the CreatableSelect "create" entry check capabilities instead of whether the method exists, and show "Linking isn't set up for this grid" instead of calling.
- `defineGrid` `updateSchema` rejects a newly added or retyped column the source can't back: 400 with `"<label>" can't be a link column: this grid has no records to link to` (and an equivalent for user). Existing unchanged columns are allowed.
