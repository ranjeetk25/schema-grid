# @ranjeetk25/schema-grid-server v1 Implementation Plan

**REQUIRED SUB-SKILL: superpowers:subagent-driven-development**

**Goal:** Build `@ranjeetk25/schema-grid-server`, a Node-only package that turns the core contract (spec §4) into safe, permission-checked MySQL queries and writes using Drizzle. It covers filtering, search, sort, offset/cursor paging, grouping, formula columns, optimistic writes, a change feed, schema validation, DDL helpers and import/export hooks. It also provides `createDrizzleDataSource`, which returns a core `DataSource`.

**Architecture:** Each grid has its own table of rows. Every row has fixed columns (`id`, `grid_id`, `version`, `updated_at`, `updated_by`, `deleted_at`) plus a `cells` JSON document. Every column the grid reads, filters or sorts goes through one resolver, which returns a SQL expression from one of three places:
- a physical column (`source.valueField`),
- a generated column `gc_<key>` (for `indexed: true` columns and materialized formulas),
- a JSON path into `cells`, cast to the right type.

On top of this resolver sit small pure translators (filter, search, sort, keyset, grouping, formula). Each returns Drizzle `SQL` and gets snapshot tests through `.toSQL()` or `MySqlDialect.sqlToQuery`. `buildQuery` checks permissions and puts the pieces together. The write path (`applyChanges`, `createRows`, `deleteRows`) runs in one transaction and writes a `change_log` table, which `getChanges` reads from. All core types and functions come in through one internal file (`src/internal/core.ts`) and are never redefined.

**Tech Stack:** TypeScript (strict), Bun workspaces, drizzle-orm ^0.45 (peer, `mysql2` dialect), mysql2 (dev/peer), Zod (via core field types), Vitest 3, `@testcontainers/mysql` (integration only, gated by env var), tsup (ESM+CJS), Biome.

**Commands:**
- Unit tests: `bun run --filter @ranjeetk25/schema-grid-server test`
- Typecheck: `bun run --filter @ranjeetk25/schema-grid-server typecheck`
- Integration tests: `SCHEMA_GRID_MYSQL_IT=1 bun run --filter @ranjeetk25/schema-grid-server test` (requires Docker; skipped when the variable is not set)

## Global conventions (apply to every task)

- **TDD.** Write the failing test first, run it and watch it fail, write the smallest code that passes, re-run, then run typecheck. Every task ends with `test` and `typecheck` green.
- **Core imports.** Import core only through `src/internal/core.ts`. Never redeclare a core type. If a core function isn't ready yet, the task stops (blocked) instead of stubbing a stand-in.
- **No string-built SQL from user input.** Values are always bound parameters. The only strings placed raw into SQL are column keys that `assertSafeColumnKey` has already checked, and fixed SQL keywords.
- **SQL snapshots.** Tests store `{ sql, params }` pairs as Vitest snapshots and also assert the params explicitly, so a changed snapshot can't hide a changed binding.
- **Style.** Biome, double quotes. Never run `check:fix` or `format` automatically.
- **Commits.** Implementers commit their own task. Every commit message ends with `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.

### Storage invariants (set in T3/T5, relied on everywhere)

- **Empty values.** An empty value (`null`, `""`, `[]`, or `undefined` after serialize) is stored by removing the key from `cells` (`JSON_REMOVE`), never as JSON `null`. The reason: `JSON_UNQUOTE` turns JSON `null` into the string `'null'`. Reads still treat JSON `null` (`JSON_TYPE = 'NULL'`) as empty, for rows written before this rule existed.
- **Stored formats.**
  - date: `YYYY-MM-DD`
  - datetime: UTC ISO with milliseconds and `Z`
  - number/currency: JSON number
  - boolean: JSON boolean
  - multiSelect: JSON array of option ids
  - select/creatableSelect: option id string
  - user/link: whatever core's `serialize` produces. The storage-kind table records a sub-path (for example `.id`) if the value is an object.
- **Case-insensitive text.** Text read from JSON has collation `utf8mb4_bin`, which is case-sensitive. Text expressions add `COLLATE utf8mb4_0900_ai_ci` so `contains`/`is` ignore case.
- **Column keys.** Keys must match `^[A-Za-z][A-Za-z0-9_]{0,47}$`, so `gc_<key>` and `idx_gc_<key>` fit MySQL's 64-character identifier limit.
- **Nulls in sort.** Nulls sort last in both directions. This must match core's in-memory `compare`; T11 confirms it with a parity test once C-memory is ready.

## Task 5: Column expression resolver

**Goal:** One function that, for any ColumnDef, returns the SQL expression to use for filtering, sorting, grouping and search.

**Files:** `src/sql/storage-kind.ts`, `src/sql/column-expr.ts`, `src/sql/like.ts`

**API:**
- `StorageKind`: `"text"|"number"|"boolean"|"date"|"datetime"|"choice"|"multi"|"ref"|"json"`.
- `storageKindOf(column, registry, overrides?)`:
  - text/longText/url/email/phone → text
  - number/currency → number
  - select/creatableSelect → choice
  - user/link → ref (with sub-path)
  - multiSelect → multi
  - formula → the kind of its `inferResultType`
  - unknown custom types → json (only isEmpty/isNotEmpty can be translated)
- `ColumnExprOptions`: `{ tables, generatedColumns: "assumePresent"|"ignore" }`.
- `resolveColumnExpr(column, ctx, options)` returns `{ raw: SQL, typed: SQL, kind, source: "physical"|"generated"|"json" }`. The source is chosen in order: `source.valueField` physical column, then `gc_<key>` when `indexed` and generated columns are assumed present, then JSON.
- `typedJsonExpr(key, kind)` gives the typed form:
  - text/choice/ref → `JSON_UNQUOTE(JSON_EXTRACT(cells, path)) COLLATE utf8mb4_0900_ai_ci`
  - number → `CAST(... AS DECIMAL(38,10))`
  - date → `CAST(... AS DATE)`
  - datetime → `CAST(REPLACE(REPLACE(..., 'T', ' '), 'Z', '') AS DATETIME(3))`
  - boolean → compared as the JSON boolean
- `isEmptyExpr(column, ...)`:
  - key absent, OR `JSON_TYPE = 'NULL'`, OR, by kind:
    - text: equals `''`
    - multi: `JSON_LENGTH = 0`
  - physical columns: `IS NULL` (text physical columns also match `''`)
- `escapeLike(s)` escapes `%`, `_` and `\`.

**Test:** `test/unit/sql/column-expr.test.ts`, `test/unit/sql/like.test.ts`
- Snapshot of the typed expression for each kind.
- A physical-source column resolves to the table column (no JSON).
- An indexed column resolves to `gc_<key>`; the same column with `generatedColumns: "ignore"` resolves to JSON.
- The datetime cast text is exactly the one Task 6's generated column uses (a shared constant is asserted).
- `isEmptyExpr` for multi includes JSON_LENGTH.
- `escapeLike("50%_a\\")` escapes all three special characters.

**Commit:** `feat(server): column expression resolver with typed json casts`

## Task 7: translateFilter core + text/number/boolean operators

**Goal:** Recursive AND/OR translation, a lookup table of operator translators, and the null rule driven by the operator's `negative` flag.

**Files:** `src/filter/translate-filter.ts`, `src/filter/operator-table.ts`, `src/filter/ops-text.ts`, `src/filter/ops-number.ts`, `src/filter/ops-boolean.ts`, `src/internal/core.ts` (add value re-exports as needed)

**API:**
- `translateFilter(node, schema, registry, ctx)` returns `SQL | undefined` (undefined for a null or empty filter).
  - Groups become parenthesized `and(...)`/`or(...)`.
  - Conditions go through `OperatorTranslator`s keyed by `(StorageKind, operatorId)`.
- `OperatorTranslator` type: `(args: { expr, column, value, ctx }) => SQL`.
- `registerOperatorTranslator(kind, operatorId, fn)`, so custom field types can plug in.
- **Null rule.** Look up the operator def in `registry.get(type).operators`:
  - `negative: true` wraps as `(<cmp> OR <expr> IS NULL)`, using `isEmptyExpr`, so JSON null and `''` are included too.
  - Positive operators AND with NOT empty where needed, so they never match empty values.
- Text operators: `contains` / `notContains` (LIKE with escape), `startsWith`, `is` / `isNot`, `isEmpty` / `isNotEmpty`.
- Number operators: eq, neq, lt, lte, gt, gte, `between` (inclusive `{from, to}`), isEmpty, isNotEmpty.
- Boolean operators: isTrue, isFalse. Both are positive, so empty matches neither.
- An unknown operator throws `UnsupportedOperatorError`.

**Test:** `test/unit/filter/translate-filter.text-number.test.ts`
- `isNot "Paid"` on a text column gives SQL containing `(expr <> ? OR expr IS NULL ...)`, and the param is `"Paid"`.
- `notContains "x"` includes the empty branch. `contains` does not, and its param is `%x%` escaped.
- `neq 5` includes nulls; `gt 5` excludes them and has a DECIMAL cast.
- `between {from: 1, to: 10}` binds two params.
- `isFalse` does not match empty (snapshot has no IS NULL branch).
- A nested `or` inside `and` is parenthesized correctly (snapshot).
- An empty AND group returns undefined. An unknown operator throws.
- A custom translator registered for kind `json` is used.

**Commit:** `feat(server): filter translation core with negative-null semantics`

## Task 9: Date/datetime operators and relative dates

**Goal:** Date filters with half-open ranges, relative dates resolved through core in `ctx.tz`, and no dependency on MySQL's timezone tables.

**Files:** `src/filter/ops-date.ts`, `src/sql/dates.ts`

**API:**
- `toMysqlUtc(iso)` returns `YYYY-MM-DD HH:MM:SS.fff`.
- `toLocalDate(iso, tz)` returns `YYYY-MM-DD` using Intl.
- Operators: `is`, `isBefore`, `isAfter`, `isBetween`, `isWithin` (RelativeDate), `isEmpty`, `isNotEmpty`.
- **Relative dates.** `resolveRelativeDate(rd, ctx.now(), ctx.tz)` returns `{ from, to }`, where `to` is exclusive.
  - datetime: `expr >= ? AND expr < ?` with UTC params.
  - date: both bounds converted with `toLocalDate(…, tz)`, then `expr >= ? AND expr < ?`.
- `is` with a plain date on a datetime column means that local day in tz, as `[start, next-start)`.
- All date operators are positive (empty never matches).

**Test:** `test/unit/filter/translate-filter.date.test.ts`
- With `now = 2026-09-25T00:30:00+05:30` (UTC 2026-09-24T19:00Z), tz `Asia/Kolkata`, `isWithin {relative: "yesterday"}` on a date column binds `2026-09-24` and `2026-09-25`. It must not be the UTC-based day.
- The same filter on a datetime column binds `2026-09-23 18:30:00.000` and `2026-09-24 18:30:00.000`.
- `lastNDays n=7` binds a 7-day window.
- Running the same AST with `now` one day later binds bounds shifted by one day (the saved view keeps meaning "yesterday").
- `isBetween` is inclusive of `to` for date columns (document the choice; it must match core's in-memory behaviour).
- `isEmpty` on a date column uses `isEmptyExpr`.

**Commit:** `feat(server): date operators with tz-resolved relative dates`

## Task 10: Search translation

**Goal:** Free-text search across readable text-like columns.

**Files:** `src/search/translate-search.ts`

**API:**
- `translateSearch(search, schema, registry, access, ctx)` returns `SQL | undefined`.
- The search term is trimmed and LIKE-escaped, then matched as an OR of `expr LIKE ?` over columns that are both readable and searchable.

## Task 20: applyChanges write path

**Goal:** Optimistic writes, one version bump per row, conflicts reported with the server's state, and the change log written in the same transaction.

**Files:** `src/changes/apply-changes.ts`, `src/changes/change-log.ts`

**API:**
- `applyChanges(batch, ctx, deps: { db, tables, gridId })` returns ChangeResult. Inside one `db.transaction`:
  1. SELECT current rows by id, scoped to the grid.
  2. `planChanges`.
  3. For each row plan, run `UPDATE rows SET cells = JSON_REMOVE(JSON_SET(cells, path, CAST(? AS JSON), ...), ...)`, set physical columns, `version = version + 1`, `updated_at = ?`, `updated_by = ?`, `WHERE id = ? AND grid_id = ? AND version = ? AND deleted_at IS NULL`.
  4. If affectedRows is 0, re-read the row and add a conflict for each planned cell: `serverValue` (projected), `serverVersion`, `updatedBy`, `updatedAt`.
  5. Otherwise, collect those changes into `applied`.
  6. Bulk-insert change_log entries for the applied cells: `kind "cell"`, `prev`, `next`, `actor = ctx.user.id`, `at`, `batch_id = batch.id`.
- The version always changes, so affectedRows is correct whether or not `CLIENT_FOUND_ROWS` is set.
- `buildRowUpdate(plan, ctx, tables)` is exported so it can be snapshot-tested.

**Test:** `test/unit/changes/apply-changes.test.ts` (mock db plus a fake transaction executor that returns affectedRows)
- Snapshot of the UPDATE for a row with two JSON cells, one physical cell and one emptied cell (JSON_REMOVE).
- The version is bumped once per row, not once per cell.
- affectedRows 0 produces conflicts carrying server values and no log rows for that row.
- Mixed batch: row A is applied, row B conflicts, row C errors. The result has all three buckets and log inserts only for A.
- `batch_id` and `actor` are set on log rows.

**Commit:** `feat(server): optimistic applyChanges with change log`

## Open questions / coordination with other plans

1. **Core names not fixed by the spec.** The spec doesn't define the shape of `GroupResult`, `Access`, `Option`, `LinkRef` or `ActorRef`, or the stored form of `user`/`link` values. Tasks 5, 8 and 17 adapt to whatever core publishes.
2. **Core in-memory evaluator and fixture.** Core needs to export its in-memory filter/sort evaluator and the shared fixture (ideally at `./testing`). Tasks 16, 24 and 25 depend on this; if the fixture isn't exported, it's copied as noted in Task 24.
3. **Filter depth for pinned groups.** The pinned-group AND wrapper can reach depth 3. Either core's `validateFilter` gets a `maxDepth` option, or the server's special case (T13/T17) stays and is documented for the ag-grid adapter.
4. **Behaviours that must match core.** Nulls-last sort, inclusive `isBetween`, and division-by-zero results must match core; T25 enforces this.
