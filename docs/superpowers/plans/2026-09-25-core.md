# @ranjeetk25/schema-grid-core — Implementation Plan

**REQUIRED SUB-SKILL: superpowers:subagent-driven-development**

**Goal:** Build `packages/core` (`@ranjeetk25/schema-grid-core`). It is the framework-free contract every other schema-grid package builds on:
- schema types and migrations
- a field-type registry with all 16 built-in types
- the filter AST, its validation and relative-date resolution
- the query, row, change and feed model
- the DataSource interface
- permissions
- a formula engine
- event types
- an in-memory DataSource that defines the reference behaviour every other package tests against.

**Architecture:** Pure TypeScript with no React, AG Grid, Mantine or Drizzle, and no runtime dependencies other than the `zod` peer. The code is split into small modules under `src/` by domain: schema, field-types, filter, query, rows, permissions, formula, events, time, memory. Each built-in field type lives in its own file so they can be built in parallel. There are five public entry points: `.`, `./field-types`, `./formula`, `./filter`, `./memory`. Timezone handling uses only `Intl.DateTimeFormat` via a small zoned-time helper in `src/time`. The in-memory DataSource is built from the same pure functions (`matchesFilter`, `computeAggregate`, formula `evaluate`) that other packages use, so it is the executable definition of the semantics.

**Tech Stack:** TypeScript strict, bun workspaces, Vitest, tsup (ESM + CJS + d.ts, `sideEffects: false`), Zod peer `^3.25 || ^4` (dev: zod 4), Biome with double quotes.

**Commands (run from repo root):**
- Tests: `bun run --filter @ranjeetk25/schema-grid-core test`
- Typecheck: `bun run --filter @ranjeetk25/schema-grid-core typecheck`
- Build (Task 33 only): `bun run --filter @ranjeetk25/schema-grid-core build`

**Every task follows the same loop:** write the failing tests, run them and see them fail, implement the smallest change that passes, run test and typecheck (both green), then commit on the package branch. Never run `bun run check:fix` or `bun run format`. Add the commit attribution trailer your environment requires.

**Global rules for implementers:**
- No `any` in public types.
- The row generic is `<Row extends GridRow>`.
- Use only Zod API that exists in both v3.25 and v4: `z.object`, `z.string`, `z.number`, `z.boolean`, `z.array`, `z.enum`, `z.union`, `z.literal`, `z.nullable`, `.optional`, `.refine`, `ZodType`. Don't use `.email()` or `.url()`; validate those with in-house regexes or `URL` parsing.
- Public functions that take user input never throw. They return a result or error union. The only exceptions are `migrateSchema` (documented typed error) and the memory `fetch` (the promise rejects with a typed error).
- Cells are keyed by `ColumnDef.key`. Filters, sort, group, permissions and changes refer to `ColumnDef.id`.

  - `SchemaMigrationError` (Error subclass) with code `"gap" | "duplicate" | "versionMismatch"`.
  - `migrateSchema(schema, migrations, targetVersion?)` returns a new GridSchema. It never mutates its input.

- **Test file:** `packages/core/test/schema/migrate.test.ts`
  - Applies migrations in ascending `toVersion` order even when they're passed in shuffled order.
  - Skips migrations whose `toVersion` is at or below the current schemaVersion.
  - Sets schemaVersion to each migration's `toVersion` after it runs.
  - Stops at `targetVersion` when one is given.
  - Throws SchemaMigrationError code "gap" when versions jump, for example 1 → 3 with no 2.
  - Throws code "duplicate" when two migrations share a `toVersion`.
  - Throws code "versionMismatch" when a migrate function returns a schemaVersion different from its `toVersion`.
  - Does not mutate the input schema (checked with a deep-frozen input).
  - With no applicable migrations, returns a structurally equal schema.
  - The lookup helpers find by id and by key and return undefined for unknown values.

  - A formula column with edit "all" resolves to read.
  - A column without permissions resolves to edit.
  - superRoles gets edit on a restricted column and read on a formula column.
  - `resolveColumnAccess` returns an entry for every column id, and `readableColumnIds` excludes the hidden ones.

## Task 8: Zoned time helpers and resolveRelativeDate

- **Goal:** Resolve relative dates correctly across timezones using only `Intl`, as half-open ranges with weeks starting on Monday.
- **Files:**
  - `src/time/zoned.ts`
  - `src/filter/relative-date.ts`
- **Public API:**
  - `DEFAULT_TIME_ZONE = "Asia/Kolkata"`
  - `getZonedParts(instant: Date, tz)`: returns `{ year, month, day, hour, minute, second, weekday (1=Mon..7=Sun) }` via `Intl.DateTimeFormat#formatToParts`.
  - `zonedToInstant(parts, tz)`: returns a Date. It uses an iterative offset fix-up so it handles DST gaps and overlaps; in a gap it picks the later valid instant.
  - `startOfZonedDay(instant, tz)`
  - `addCalendarDays({year,month,day}, n)`
  - `resolveRelativeDate(rd, now: Date, tz = DEFAULT_TIME_ZONE)`: returns `DateRange` with from and to as UTC ISO strings ending in "Z", meaning `[from, to)`.
- **Semantics:**

  | Kind | Range |
  |---|---|
  | today | [start of today, start of tomorrow) |
  | yesterday | [start of yesterday, start of today) |
  | tomorrow | [start of tomorrow, start of the day after) |

- **Goal:** Validate filters structurally and against the schema, returning typed errors.
- **Files:** `src/filter/validate.ts`

  | Kind | Valid value |
  |---|---|
  | none | value absent |
  | single | a primitive |
  | multi | a non-empty primitive array |
  | range | `{from, to}` |
  | relativeDate | a RelativeDate, and n is required for lastNDays and nextNDays |

## Task 28: matchesFilter

- **Goal:** Provide the reference filter semantics in JS, shared by the memory source and any client-side filtering.
- **Files:** `src/filter/match.ts`
- **Public API:**
  - `FilterMatchContext { schema, registry, now: Date, tz: string, userId?: string }`
  - `matchesFilter(node, row, ctx)`: returns boolean. A null node matches.
  - Rows are expected to be pre-validated; unknown columns or operators never match.
- **Semantics:**
  - Negative operators return true when the cell is empty. Positive operators return false when it's empty.
  - Text comparisons are case-insensitive.
  - Select `is` compares option ids.
  - multiSelect:
    - hasAnyOf means the arrays intersect.
    - hasAllOf means the value contains every filter id.
    - hasNoneOf means no intersection.
  - Date and datetime:
    - `is` (date) means the same calendar day in tz.
    - isBefore and isAfter are strict.
    - isBetween is inclusive on both ends, as the user sees it.
    - isWithin resolves the range with `resolveRelativeDate(now, tz)` and tests `from <= t < to`. Date values are converted to the start of that day in tz.
  - user: isMe compares with `ctx.userId`; with no userId, isMe is false and isNotMe is true.
  - link: `is` and isAnyOf match on LinkRef ids.
  - boolean: isTrue and isFalse compare strictly.
  - Formula columns: evaluated per the column's resultType. The caller passes materialised values in cells.
- **Test file:** `packages/core/test/filter/match.test.ts`
  - **Must include (negative operators match empty values):** each of isNot, isNoneOf, notContains, neq, hasNoneOf and isNotMe matches rows whose cell is null, undefined, "" or [], as appropriate to the type.
  - Every positive operator (is, isAnyOf, contains, eq, lt, hasAnyOf, isMe, startsWith, isWithin) does NOT match an empty cell.
  - **Must include (Kolkata isWithin yesterday):** with now = 2026-09-25T02:30+05:30 and tz Asia/Kolkata:
    - a datetime at 2026-09-24T00:00+05:30 matches
    - 2026-09-24T23:59:59+05:30 matches
    - 2026-09-25T00:00+05:30 does not match (the end is exclusive)
    - 2026-09-23T23:59+05:30 does not match
    - a date column value "2026-09-24" matches and "2026-09-25" does not
  - Spec §8 scenario across three rows (status Paid, status Pending, status null, all with callDate yesterday): "status isNot Paid AND callDate isWithin yesterday" matches Pending and null, not Paid.
  - An or group matches when any child matches; an and group needs all of them; an empty and group matches everything; an empty or group matches nothing.
  - number between is inclusive.
  - Text contains is case-insensitive.
  - hasAllOf needs every id.
  - isFalse does not match null. It isn't negative, so this is documented behaviour.
- **Commit:** `feat(core): add reference matchesFilter semantics`

## Task 31: In-memory mutations with version checks

- **Goal:** Implement applyChanges, createRows and deleteRows with optimistic concurrency.
- **Files:**
  - Create `src/memory/mutations.ts`.
  - Wire it into `src/memory/data-source.ts`.
- **Semantics for applyChanges:**
  1. Group the changes by rowId.
  2. Per change, record an error (not a throw) when:
     - the row is missing
     - the column is missing
     - the column isn't editable for the user (hidden or read-only, including formula)
     - `valueSchema` validation fails
     - the rowId is missing from `baseVersions`
  3. Per row, if `baseVersions[rowId]` differs from the current version, every change for that row becomes a conflict entry: `{ rowId, columnId, serverValue, serverVersion, updatedBy, updatedAt }`. It is not an error.
  4. Otherwise, apply the row's valid changes, increment the version once per row per batch, set `updatedAt` from `now()` and `updatedBy` from `actor`, and re-materialise formulas.
  5. Return the applied changes with the actual `prev` (server value) and `next`.

  createRows:
  - Fills defaults with `fieldType.defaultValue(config)`, then `ColumnDef.defaultValue`, then the partial.
  - Validates values; invalid partials reject.
  - Sets version 1 and generates ids.

  deleteRows:
  - Removes the rows.
  - Unknown ids are ignored.
- **Test file:** `packages/core/test/memory/mutations.test.ts`
  - A matching `baseVersions` applies the change, bumps the version from 1 to 2, and a subsequent fetch shows the new value.
  - **Must include (version mismatch gives a conflict, not an error):** with base version 1 and server version 2, `applyChanges` resolves (doesn't reject). The result has `applied` empty, one conflict entry carrying the server value, serverVersion 2, updatedBy and updatedAt, and `errors` empty.

  - Three changes on the same row bump the version by exactly 1.
  - An edit to a formula column gives an error "read-only".
  - An edit to a read-only column for the current user gives an error.
  - An edit to an unknown row gives an error.
  - An invalid value (text into a number column) gives an error and the row is left unchanged.
  - After editing fee, the balance formula recomputes.
  - createRows applies type defaults (boolean false, multiSelect []) and column defaultValue, and returns rows with version 1 and unique ids.
  - deleteRows removes the rows from later fetches, and deleting an unknown id is a no-op.

## Decisions this plan makes that the spec leaves open

These should be flagged to the other package plans.

1. **Relative-date ranges and wire format.** lastNDays and nextNDays include today. `resolveRelativeDate` returns UTC ISO strings ending in "Z".
2. **Date values.** Date columns store "YYYY-MM-DD"; datetime columns store UTC ISO. Date columns are compared against relative ranges using the start of the day in tz.
3. **Boolean isFalse.** It is not negative, so it does not match null, following the spec's "positive never matches empty" rule.
4. **Formula arithmetic.** Empty operands count as 0 (as in Airtable). Division by zero gives null. IF and COALESCE branch types must match. `+` does not concatenate text.
5. **Formula result type storage.** It lives in `ColumnDef.config.resultType`, set by the column builder from `inferResultType` when the column is saved. Filter operators for formula columns resolve through it.
6. **Always-allowed aggregations.** count, countEmpty and countFilled are allowed on every type. sum and avg only where the type declares them.
7. **Partial batches.** A conflict on one row doesn't block other rows in the same batch. The version bumps once per row per batch.
8. **Cursors.** Memory feed and paging cursors are opaque strings: a sequence number and an encoded offset.
9. **User values.** `UserRef` objects, single-valued in v1. Link values are always `LinkRef[]`.
10. **Pending options.** `ParseResult` includes an optional `pendingOptions` so creatableSelect and multiSelect imports can create options.
