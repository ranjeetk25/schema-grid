# @ranjeetk25/schema-grid-ag-grid — Implementation Plan

**REQUIRED SUB-SKILL: superpowers:subagent-driven-development**

**Goal:** Build `packages/ag-grid` (`@ranjeetk25/schema-grid-ag-grid`): a schema-driven layer on AG Grid Community 36. It compiles `GridSchema` into ColDefs, runs client and server (infinite) row models, and handles editing with optimistic writes and conflict handling. It also includes our own range selection, clipboard, fill handle, undo/redo, grouping, polling sync, column filters, views, CSV export and theming. It never touches AG Grid Enterprise.

**Architecture:** Pure logic (compile, filter-model conversion, range geometry, clipboard and fill planning, undo, grouping, remote patch planning, datasource adapter) lives in framework-free modules with unit tests. State lives in small hand-rolled external stores (built on `useSyncExternalStore`) and is read by AG Grid through the `context` grid option and `cellClassRules`/`rowClassRules`. Changes trigger targeted `api.refreshCells`/`redrawRows` calls rather than React re-renders. The `useSchemaGrid` hook assembles grid options, and `<SchemaGrid>` renders them. One `FilterNode` in the query store is the only source of truth for filters: column filters are a view onto it. All core imports go through one internal file so gaps in the concurrently-built core stay contained.

**Tech Stack:** TypeScript strict, React 18, `ag-grid-community`/`ag-grid-react` ^36 (peer deps; modules passed per grid via the `modules` prop, never the global registry), `@ranjeetk25/schema-grid-core` (workspace, `development` condition → src), optional peer `@ranjeetk25/schema-grid-io` (loaded with a dynamic import for XLSX only), tsup (ESM+CJS, `sideEffects: false`), Vitest 3 + Testing Library + jsdom, Biome. No zustand: stores are hand-rolled.

**Commands:** `bun run --filter @ranjeetk25/schema-grid-ag-grid test` and `bun run --filter @ranjeetk25/schema-grid-ag-grid typecheck`. Never run `check:fix`/`format`.

**Rules for every task**
- Write the failing test first, see it fail, implement, see it pass, then run typecheck, then commit on the package branch.
- Import sibling modules by relative path. Only Task 1 (stubs) and Task 32 (final) edit the barrel files `src/index.ts`, `src/editors/index.ts`, `src/filters/index.ts` and `src/sync/index.ts`. This avoids merge conflicts between parallel tasks.
- Import core only through `src/internal/core.ts`. If a core export is missing, add a minimal local type or function alias there with a comment `TODO(core): spec §4.x — replace with core export` and carry on.
- Never import `ag-grid-enterprise`. The Task 1 guard test enforces this.
- Public types are generic over `<Row extends GridRow>` and contain no `any`.

## Deviations and decisions (read first)
1. **Edit entry point: `readOnlyEdit: true` + `onCellEditRequest`.** I used these instead of `onCellValueChanged`. Both are documented Community APIs. The difference is that with `onCellEditRequest` the grid does not change row data before we do, so vetoes, transforms and rollbacks have nothing to undo. Only `src/editing/editEntry.ts` depends on this choice, so switching back is a one-file change.
2. **Client-mode sorting:** header sort is recorded into the query store. `postSortRows` then restores the order core computed. AG Grid's own ordering never wins.
3. **Client-mode filtering:** custom filter `doesFilterPass` always returns true, because rows arrive already filtered by core.
4. **Server mode with `groupBy`:** the infinite row model can't insert group rows. So when server grouping is active, the grid switches to a client-side row model that holds group shell rows. Children are lazy-loaded one page at a time, each page fetched with a pinned group filter, and a "load more" full-width row follows each group.
5. **Fill handle:** the handle element is rendered by a `CellShell` renderer that wraps every column's renderer. It only appears in the range's bottom-right cell and is absolutely positioned there. It scrolls with the grid and doesn't rely on AG Grid's private DOM classes.
6. **Package direction:** `ui-mantine` depends on `ag-grid` (it uses `createPopupEditor` and passes a `UiFieldTypeRegistry` override). `ag-grid` does not depend on `ui-mantine`. Spec §3 can be read both ways; this reading avoids a cycle.
7. **Server-mode CSV:** CsvExportModule only sees loaded blocks. So server-mode CSV and all XLSX exports fetch the full current query in pages and hand it to io.

### T9 — Edit controller (pipeline, optimistic writes, conflicts)
- **Goal:** one path for edit, paste, fill, undo and redo writes.
- **Files:** `src/editing/editController.ts`, `src/editing/conflicts.ts`, `src/editing/editEntry.ts`
- **API:**
  - `createEditController({ dataSource, rowStore, cellStatus, events, onApplied?, onReverted?, idFactory? })` returns `{ submit(changes, source), buildBatch(changes, source) }`
  - `buildBatch` fills `baseVersions` from rowStore
  - `submit` sequence:
    1. awaits `beforeCellsChange`; false vetoes, a returned batch replaces the original
    2. applies optimistically and marks cells pending
    3. calls `applyChanges`
    4. applied cells: clear pending and bump versions
    5. errors: revert and set the cell error
    6. conflicts: revert to prior, then emit `onConflict(conflict, resolve)`, where `resolve("keepTheirs"|"overwrite")` either writes the server value and version or re-submits with `baseVersions` equal to serverVersion
    7. emits `onCellsChange(result)`
    8. resolves to `SubmitOutcome { result, batch, vetoed }`
  - `createEditRequestHandler(controller)` adapts `onCellEditRequest` params into a single-cell `"edit"` submit
- **Test:** `test/editing/editController.test.ts` (in-memory data source double)
  - the veto path leaves rows untouched
  - transform replaces the changes
  - an optimistic value is visible before applyChanges resolves
  - pending clears after success
  - a server error reverts and records the message
  - a conflict reverts and calls onConflict
  - keepTheirs sets the server value and version
  - overwrite re-submits once with the new base version and the same source
  - a thrown applyChanges reverts every cell in the batch
  - onApplied reports formula dependents that need a refresh
- **Commit:** `feat(ag-grid): edit pipeline with optimistic apply and conflict resolution`

### T15 — Remote patch planning and usePollingSync
- **Goal:** polling sync logic.
- **Files:** `src/sync/planRemotePatch.ts`, `src/sync/usePollingSync.ts`, `src/sync/useDocumentVisible.ts`
- **API:**
  - `planRemotePatch({ entry: ChangeFeedEntry, rowStore, editingCell?, pendingCells, matchesView(row), currentSchemaVersion })` returns `{ updates: Row[], adds: Row[], removes: string[], changedCells, remoteChangedCells, deferred: Row[], notInViewRowIds, schemaChanged }`
    - rows whose version is not newer than the local copy are ignored (our own echoes)
    - if a changed cell is being edited or pending, that row goes to deferred and its version is not bumped, so a later commit produces a proper conflict; the cell is marked remoteChanged
    - updated rows that no longer match the view go to notInView (they are not removed)
  - `usePollingSync({ dataSource, intervalMs = 7000, enabled, initialCursor?, onEntry })` returns `{ lastCursor, lastError, pollNow }`. It keeps only one request in flight, skips polling when `getChanges` is absent, and backs off after an error.
  - `useDocumentVisible()`
- **Test:** `test/sync/planRemotePatch.test.ts`
  - a newer version produces updates and changedCells
  - an older or equal version is ignored
  - the editing cell becomes remoteChanged and deferred without a version bump
  - an update that no longer matches goes to notInView
  - deleted ids are removed
  - schemaChanged when versions differ
- **Test:** `test/sync/usePollingSync.test.ts` (fake timers)
  - polls every interval while enabled
  - stops when hidden
  - passes the previous cursor
  - never overlaps requests
  - resumes when visible again
- **Commit:** `feat(ag-grid): polling sync planner and hook`
